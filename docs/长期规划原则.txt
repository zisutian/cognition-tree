长期规划原则


文档职责：

    记录长期协作原则、提交边界和文档交互规则。
    不记录当前主线、当前 TODO、具体功能需求、工程架构、个人环境和外部使用说明。


1. 基本原则

长期工作必须围绕可审查闭环推进。

一个闭环可以是产品能力、工程边界、交互工作台、存储链路或文档体系。

默认不做无边界的大改，但也不为了“小步”把同一个闭环切得过碎。


2. 与逐步构建流程的关系

长期规划原则：

    只定义长期工作规则。
    不决定当前做什么。
    不维护具体任务列表。
    不记录某一步已经做到哪里。

逐步构建流程：

    记录当前状态、当前主线、近期顺序、验证命令和暂缓事项。
    是判断下一步工作的唯一当前路线入口。
    当前主线变化时，只修改逐步构建流程，不修改长期规划原则。

交互规则：

    长期规划原则约束逐步构建流程的写法。
    逐步构建流程不能反过来塞入长期原则。
    如果两者冲突，以长期规划原则判断文档边界，以逐步构建流程判断当前步骤。


3. 工作节奏

任务拆分：

    先判断当前工作属于产品需求、工程架构、执行流程还是个人环境。
    目标应拆成能说明完成标准、验证方式和提交边界的闭环。
    如果一个步骤无法独立审核或独立回滚，应继续拆小。

文档先行：

    路线切换、架构判断、语法判断、存储判断和工作顺序应先登记到对应文档。
    不是所有修改都必须先改文档。
    小 bug、样式细节、明显修正可以直接做，但提交说明必须说明边界。
    文档只记录所属领域的判断，不跨文档重复维护同一类信息。

文档维护：

    docs 应周期性整理，不只追加内容。
    文档过长时应优先保留当前仍有决策价值的信息，删除陈旧路线、已失效假设和重复说明。
    已经沉淀为稳定架构的内容应进入工程架构；仍在执行排序中的内容应进入逐步构建流程；只是历史过程的信息应删除。
    文档重构可以作为独立闭环处理，目标是提高可读性和判断效率，而不是保留完整讨论历史。
    删除陈旧文档内容不需要兼容旧表述，但必须避免删除仍影响当前决策的原则、边界和验证依据。

分支判断：

    涉及路线切换、运行形态切换、架构删除、大规模重构或长期实验时，应先考虑是否新建或切换分支。
    main 不应承载未确认的新路线叙述。
    分支语义应在 docs 或提交说明中保持清楚。

执行：

    每次只执行当前闭环。
    当前步骤完成后，应运行与该步骤风险匹配的检查。
    不顺手推进下一闭环，除非已经明确得到继续指令。

审核：

    每个闭环完成后先停下汇报。
    由用户检查界面、文档、代码或行为是否符合预期。
    用户未确认前，不进行提交。

提交：

    只有用户明确允许提交后，才进行本地提交。
    提交前必须确认工作区变更范围清楚。
    提交信息应描述本步骤的真实边界。
    后续提交默认使用标题加正文的形式，正文说明主要变更、边界和验证情况。
    提交粒度可以适当放大，以完整可审查的功能闭环或架构步骤为单位，避免过度碎片化。


4. 必须停顿点

以下情况必须停下等待审核：

    产品需求边界变化后。
    工程架构边界变化后。
    当前主线变化后。
    可见 UI 行为变化后。
    运行方式或存储方式变化后。
    删除文件、删除兼容入口或删除旧路线后。
    准备提交前。
    需要决定是否切分支前。


5. 验证原则

验证范围随步骤风险调整。

长期规划原则只规定验证选择方式，不维护具体命令清单。

具体命令由 docs/逐步构建流程.txt 维护。

选择验证时应考虑：

    文档改动至少检查空白错误和关键词残留。
    领域规则或解析器改动至少运行相关单元测试。
    前端和 TypeScript 改动至少运行类型检查。
    构建、运行方式、后端脚本和 Docker 改动应运行逐步构建流程中登记的对应命令。
    如果当前步骤风险超过逐步构建流程登记的命令，应在汇报中说明补充验证。


6. 文档归属

README.md：

    面向使用者和普通开发者。
    记录项目简介、运行环境、开发命令、代码结构、许可证和依赖策略。

docs/产品需求.txt：

    记录产品定位、设计原则、核心概念、语法需求、功能范围、风险和成功标准。

docs/工程架构.txt：

    记录工程路线、分层架构、源码目录、数据流、存储边界和后续工程约束。

docs/逐步构建流程.txt：

    记录当前状态、当前主线、近期任务、验证命令和暂缓事项。
    不记录产品原则、详细需求、长期架构和长期流程规则。

docs/环境准备.txt：

    只记录当前开发者的本机环境、双机分工和待确认项。

docs/长期规划原则.txt：

    当前文件。
    记录长期协作原则、提交边界和文档交互规则。

规则：

    新内容必须先判断唯一归属。
    不在多个文档重复维护同一类信息。


7. 例外

简单错别字、明显格式错误、无争议的小文档修正可以直接执行，但仍不自动提交。

涉及用户已经明确要求的连续执行时，也应在每个完成环节汇报当前状态。
