长期规划原则

日期：2026-06-05


文档职责：

    记录长期工作方式和流程约束。
    不记录具体功能需求、当前 TODO、个人环境和外部使用说明。


1. 基本原则

长期工作必须按小步推进。

每一条主线都应先拆分，再登记，再判断是否需要分支，然后执行、审核和提交。

默认不做一口气大改。


2. 标准流程

第一步：分步骤

    先把目标拆成可以单独验证的小步骤。
    每一步都应有清楚的完成标准。
    如果一个步骤无法独立说明或独立验证，应继续拆小。

第二步：写入必要 docs

    重要路线、架构判断、语法判断、存储判断和工作顺序应先写入 docs。
    docs 更新完成后，才进入对应代码步骤。
    小 bug、样式细节、明显修正不强制先写 docs，但应在汇报或提交说明中交代边界。
    docs 只记录内部判断，不替代 README 的外部入口职责。

第三步：分支判断

    涉及路线切换、运行形态切换、架构删除、大规模重构或长期实验时，应先考虑是否新建或切换分支。
    main 不应承载未确认的新路线叙述。
    分支语义应在 docs 或提交说明中保持清楚。

第四步：执行 step

    每次只执行当前步骤。
    当前步骤完成后，应运行与该步骤风险匹配的检查。
    不顺手推进下一步骤，除非已经明确得到继续指令。

第五步：用户审核

    每个步骤完成后先停下汇报。
    由用户检查界面、文档、代码或行为是否符合预期。
    用户未确认前，不进行提交。

第六步：提交

    只有用户明确允许提交后，才进行本地提交。
    提交前必须确认工作区变更范围清楚。
    提交信息应描述本步骤的真实边界。
    后续提交默认使用标题加正文的形式，正文说明主要变更、边界和验证情况。
    提交粒度可以适当放大，以完整可审查的功能闭环或架构步骤为单位，避免过度碎片化。


3. 停顿点

以下情况必须停下等待审核：

    docs 结构调整完成后。
    架构判断写入文档后。
    单个实现步骤完成后。
    运行方式或存储方式变化后。
    删除文件、删除兼容入口或删除旧路线后。
    准备提交前。
    需要决定是否切分支前。


4. 验证原则

验证范围随步骤风险调整。

文档步骤至少检查：

    git diff --check
    相关关键词无残留或无矛盾引用

前端或 TypeScript 步骤至少检查：

    pnpm test
    pnpm check
    git diff --check

构建或运行方式步骤还应检查：

    pnpm build
    node --check server/index.mjs
    node --check server/workspaceApiServer.mjs
    node --check server/workspaceFileStore.mjs
    node --check server/syntaxProfileToml.mjs

Docker 步骤还应检查：

    docker compose config


5. 文档归属

README.md：

    面向使用者和普通开发者。
    记录项目简介、运行环境、开发命令、代码结构、许可证和依赖策略。

docs/产品需求.txt：

    记录产品定位、设计原则、核心概念、语法需求、功能范围、风险和成功标准。

docs/工程架构.txt：

    记录工程路线、分层架构、源码目录、数据流、存储边界和后续工程约束。

docs/逐步构建流程.txt：

    记录当前状态、当前主线、近期任务、验证命令和暂缓事项。

docs/环境准备.txt：

    只记录当前开发者的本机环境、双机分工和待确认项。

docs/长期规划原则.txt：

    当前文件。
    记录长期工作方式、文档归属和流程约束。

规则：

    新内容必须先判断唯一归属。
    不在多个文档重复维护同一类信息。


6. 例外

简单错别字、明显格式错误、无争议的小文档修正可以直接执行，但仍不自动提交。

涉及用户已经明确要求的连续执行时，也应在每个完成环节汇报当前状态。
