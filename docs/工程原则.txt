工程原则


1. 目的

工程原则只约束代码如何长期保持清楚和可演进。产品事实、架构边界、运行方式和界面约束分别放在对应专题文档，不在这里重复。


2. 一致性

代码围绕稳定概念组织，不围绕一次性页面状态组织。同类对象使用一致的命名、数据形态、命令、错误和交互反馈；领域差异通过明确类型、参数或策略表达。

命名必须说明事实职责，文件位置必须说明所属层次。导入方便不能改变所有权。遇到同名不同物或异名同物，应同时检查数据类型、调用链和同类实现。


3. 划分与复用

功能在职责自然结束处拆分，在确有共同模型、流程或渲染结构时合并。

复用前先区分：

    领域模型
    查询与投影
    view model
    UI 结构

数据来自同一处不代表属于同一层；视觉相似也不代表业务语义相同。重复的结构性能力进入共享层，页面只保留业务布局、局部状态和回调组装。


4. 状态与副作用

    core 承载纯领域规则与命令。
    application 承载框架无关用例、session、导航、问题和协调。
    infrastructure 承载存储、网络和平台实现。
    presentation 承载 React、编辑器和交互。
    contracts 只描述 wire shape 与运行时解析。

每份状态必须有唯一权威来源；解析、索引、图谱、结构树和 UI 投影通过明确入口派生。副作用、CAS、重试和错误暴露必须位于可识别的边界。


5. 修改方式

修改前判断问题属于命名、数据结构、职责、层次、复用还是边界泄漏，再落到正确所有者。不要用旁路、隐藏默认、临时开关或重复状态掩盖结构问题。

长期修改应减少下一次相关变更的成本，同时保持现有事实可验证。


6. 测试

单元和组件测试按生产职责组织，验证稳定输入输出与公开语义。测试辅助函数留在对应测试域，不从生产模块导出仅供测试的内部判断。

架构测试约束依赖方向、唯一所有者和禁止边界，不锁定偶然文件清单。样式规则集中在 design contract；shared primitive 只在自身测试中验证 class、状态类和布局变量，Activity 组件测试只验证可访问语义、状态与交互，不重复具体 DOM 排列或 CSS selector。

E2E 按独立功能域造数。共享仓库 fixture、页面入口和 Canvas 读取放入 e2e/support；测试文件不依赖彼此执行顺序，只有确实共享并修改同一数据的场景组串行。

共享状态机只在其生产 owner 完整验证，领域 wrapper 只保留接线和领域差异。负向守卫只表达长期禁止的类别，不保存退役函数、选择器或路径的墓碑清单。浏览器 E2E 只承担跨层流程和浏览器特有事实，不重复纯解析、状态机或组件内部契约。


7. 工程目录

五个源码层保持根级平行；文档、单元测试和 E2E 作为一等工程目录保留在根部。构建、Git、基准脚本和专用配置归 tooling。

所有可重建的构建、测试与缓存产物归 .artifacts，并可由 pnpm clean 统一删除。.cognition-tree 是本地内容和服务状态，不得作为缓存或清理目标。
