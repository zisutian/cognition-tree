工程原则


1. 定位

工程原则用于判断代码和结构是否能长期保持一致、清楚、可演进。

它关注命名、文件形式、职责划分、层次位置、复用边界和修改方式。产品事实、架构边界和界面约束分别记录在对应专题文档中。


2. 长期一致性

代码结构围绕稳定概念展开，而不是围绕一次性页面状态展开。

同一类对象使用同一套命名、数据形态和操作语言。同一类流程使用相同的输入、输出和错误暴露方式。同一类 UI 结构使用一致的行结构、状态表达和交互反馈。

局部能力可以有自己的交互细节。基础结构保持统一，业务差异通过明确的类型、参数、回调或模式表达。


3. 命名和文件

命名表达事实职责。宽泛词只用于真实的上层概念，不用于遮盖边界。

文件位置表达所属层次。导入路径便利性不改变文件归属。

同名不同物和异名同物需要追到数据类型、职责边界和调用关系。纵向检查同一能力链路中的命名、数据和职责传递；横向检查同类递归、遍历、选择、拖放、行渲染和状态推导。


4. 划分和复用

功能拆分以职责自然结束为边界。功能合并以共同模型、共同流程或共同渲染结构为边界。

复用先区分模型复用、查询复用、view model 复用和 UI 渲染复用。数据来自同一处并不等于代码属于同一层；两个界面视觉相似也不等于业务语义相同。

重复出现的结构性能力进入共享层。页面只保留自身业务布局、局部状态和业务回调组装。


5. 状态和副作用

长期稳定的代码具有清楚的数据边界、状态来源、副作用位置和错误暴露边界。

workspace 命令承载业务修改。application 管理 session、选择状态、保存流程和视图投影。ui 表达展示结构和用户交互。editor 适配编辑器技术能力。storage 和 server 承载持久化端口与执行。

派生数据通过明确入口生成。解析、索引、图谱、结构树和 UI 投影各自保留清楚的输入输出。


6. 修改方式

修改先判断问题属于命名、数据结构、职责划分、层次位置、复用缺失还是边界泄漏，再决定落点。

结构问题直接回到正确层次修正。旁路、隐藏默认、额外开关和临时分支会扩大长期维护面。

一次长期修改的结果应让下一次相关能力更容易落位，而不是只让当前样例能够运行。
