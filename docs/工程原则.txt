工程原则


1. 定位

工程原则用于判断代码和结构是否能长期保持一致、清楚、可演进。

本文件不记录产品事实，不重述架构边界，不替代产品需求、架构边界和界面样式约定。
这些文档是已有约束，不能为了当前局部实现随意改写。

工程原则关注如何写出工程性更强的代码：

    命名是否准确。
    文件形式是否自然。
    功能划分是否合理。
    位置是否符合职责。
    抽象是否来自真实重复和稳定边界。
    局部实现是否破坏长期一致性。


2. 长期一致性

代码结构应围绕稳定概念展开，而不是围绕临时页面、临时状态或一次性需求展开。

同一类对象使用同一套命名、数据形态和操作语言。
同一类流程使用相同的输入、输出和错误暴露方式。
同一类 UI 结构使用一致的行结构、状态表达和交互反馈。

局部功能可以有自己的交互细节，但不应该创造一套新的基础结构。
特殊情况只有在代表真实业务差异时才进入结构，否则应回到已有模型、查询、view model 或 UI 结构中表达。


3. 文件和命名

逐文件判断文件命名是否合理、文件形式是否自然、功能划分是否合理、位置是否合理。

同名不同物和异名同物都要追到数据类型、职责边界和调用关系，不能只按文件名判断。

纵向检查同一能力链路中的命名是否统一、数据是否连续、职责是否自然传递。
横向检查同一类数据结构、递归、遍历和渲染形态是否在不同文件重复实现。

命名应表达事实职责，不用宽泛词遮盖边界。
文件位置应表达所属层次，不为导入路径方便改变归属。


4. 划分和复用

功能拆分以职责自然结束为边界。
功能合并以共同模型、共同流程或共同渲染结构为边界。

复用前先区分模型复用、查询复用、view model 复用和 UI 渲染复用。
不要因为数据来自同一处，就把不同层次的代码放到同一文件或同一目录。
不要因为两个界面视觉相似，就合并不同业务语义。

基础结构可以复用，业务交互通过参数、回调或模式注入。
重复实现同一类递归、遍历、选择、拖放、行渲染或状态推导时，应优先抽出稳定结构。


5. 工程性

工程性优先于局部省事。

长期一致的代码应满足：

    数据边界清楚。
    状态来源清楚。
    副作用位置清楚。
    UI 展示和业务模型分离。
    派生数据有明确入口。
    错误在合适边界暴露。

不为局部功能叠加额外校验、开关、兼容入口或旁路路径。
当旧结构已经不合理时，直接修正结构，而不是在错误结构上继续包裹。


6. 修改方式

修改时按最严格情况审视，不按当前最小样例判断结构是否成立。

先判断问题属于命名、数据结构、职责划分、层次位置、复用缺失还是边界泄漏，再决定改动方式。
不为了局部功能实现影响整体层次。
不为了保留旧调用方式牺牲清楚结构。

长期修改的结果应让下一次相关能力扩展更容易落位，而不是只让当前改动刚好能运行。
