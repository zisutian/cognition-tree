产品需求


文档职责：

    记录产品定位、设计原则、核心概念、语法需求、功能范围、风险和成功标准。
    不记录源码目录、开发命令、个人环境、提交计划和工程执行顺序。


1. 产品定位

认知树不是 Markdown 编辑器，也不是传统富文本笔记软件。

认知树的目标是构建一个“可配置语法的认知树编辑器”，用于记录概念、概念群组、定义、组分、自我理解、代码片段和关系。

用户写作时面对的应是思维结构，而不是 Markdown、HTML 或其他排版格式。

Markdown、HTML、PDF、纯文本只作为导出格式，不作为主要写作格式。


2. 设计原则

思维优先：

    编辑器优先服务思维链路，而不是服务文档排版。

缩进即作用域：

    缩进代表父子关系、展开关系或局部语义范围。

符号即语义：

    行首符号、行内符号和块头符号应映射为明确语义。

语法可配置，底层结构稳定：

    用户可以调整符号表达的含义和显示提示。
    行、缩进、父子关系和引用语义必须保持稳定。

语法文件独立：

    语法配置应独立于普通笔记正文。
    每个仓库维护一份语法配置。
    仓库内所有笔记使用同一份仓库语法。

仓库即知识域：

    仓库是长期知识域和本地文件夹边界，不是单篇笔记的位置。

目录只负责组织：

    文件夹用于浏览、归类、移动和决定新建笔记落点。
    文件夹不绑定语法、不继承语法、不保存解析配置。

本地优先：

    笔记优先保存在本地，用户拥有完整数据。

可导出：

    软件不能制造数据囚笼，笔记必须可以导出为开放格式。


3. 核心概念

仓库：

    长期存在的知识域，接近 Obsidian vault。
    仓库持有笔记原文、目录树、仓库语法、笔记元信息和索引缓存。

文件夹：

    仓库内的组织结构，只负责组织和浏览。

笔记：

    用户记录一个相对完整认知对象的内容单元。
    笔记应保留原文，并由仓库语法统一解析。

块：

    认知树笔记的基本结构单位，由一行及其缩进子树组成。
    用户移动、阅读和理解结构时，应以整棵块子树为单位。

概念：

    普通行默认表示概念。

定义：

    对概念含义的说明。

组分：

    概念的组成部分、分类项、例子或枚举项。

自我理解：

    用户当前的个人解释，不要求等同于权威定义。

代码块：

    用于记录代码、伪代码、公式或严格文本。

语法配置：

    用户为仓库维护的符号解释方案。
    它决定哪些符号代表定义、组分、自我理解、代码等结构。


4. 默认语法

默认块级语法：

    普通行：概念
    :：定义
    >：自我理解
    -：组分、分类、例子和枚举的统一结构项
    ```：代码块 fence

默认行内结构：

    `...`：行内代码
    <...>：当前笔记内的局部概念引用
    [[...]]：全局概念引用
    \：并列分隔

缩进规则：

    Tab 在编辑器中插入四个空格。
    缩进表示当前行属于上一层块。


5. 语法配置需求

语法配置以仓库为管理边界。

每个仓库只维护一份当前语法配置。

语法配置只负责定义行首符号、行内符号、用户可见名称、解析角色和受控高亮提示。

笔记不单独选择语法，文件夹也不参与语法。

语法应支持：

    定义行首符号对应的块含义。
    定义行内符号对应的局部结构。
    定义界面中展示给用户的名称。
    为不同结构提供受控的视觉提示。
    将代码块作为特殊结构处理。

语法不应支持：

    改变缩进和父子关系的基础规则。
    在普通笔记正文中嵌入可执行语法配置。
    为单篇笔记单独指定语法。
    在同一仓库内混用多套语法。
    任意脚本、任意样式或不可控扩展。

语法文件管理：

    语法文件是仓库资源，不属于笔记目录树。
    仓库只有一个语法文件。
    用户可以编辑仓库语法文件。
    保存前必须校验配置是否有效。
    语法文件无效时显示明确错误，不使用内置默认语法静默解析。


6. 编辑器需求

基本编辑：

    创建笔记
    编辑认知树原文
    Tab / Shift+Tab 调整层级
    自动识别块类型
    展示诊断
    展示结构树
    支持折叠和滚动

跨笔记块移动：

    支持同一仓库内跨笔记移动。
    移动单位是整棵块子树，不移动单行碎片。
    块移动功能只做移动，不做复制。
    用户应能在两篇笔记的结构之间直接拖拽组分或其他块。
    拖拽释放到有效目标时应直接完成迁移，而不是只改变选择状态。
    第一版块移动不保留点击移动命令。
    迁移界面采用双视图模式：笔记选择视图和块迁移视图。
    笔记选择视图应允许用户通过拖拽源笔记到目标笔记完成配对。
    块迁移视图的拖拽源必须来自源笔记结构树，而不是只依赖行号列表。
    开始拖拽源块时必须展示将被移动的整棵子树范围。
    目标位置必须通过拖放到目标笔记结构树确定。
    拖到某个目标块后，应只在该目标块附近显示上方并列、下方并列和作为子结点三类投放位置。
    不能在拖拽开始后把所有目标块的投放位置同时展开。
    目标笔记还应提供文末根块投放位置。
    块迁移发生在同一仓库语法环境内，不需要为目标笔记单独检查语法差异。

结构视图：

    原文编辑区和结构树应保持联动。
    结构树只展示解析结果，不展示语法配置细节。
    当前笔记结构树服务单篇笔记阅读和定位，不承担全仓库关系总览。

仓库可视化页面：

    仓库应提供类似 Obsidian 图谱的点状统计视图。
    点代表笔记、概念或后续可扩展的块级对象。
    线代表明确引用关系，优先展示笔记之间的全局概念引用。
    用户应能看出哪些笔记互相引用、哪些节点被集中引用、哪些节点孤立。
    点状统计视图必须保持高性能，不能因为仓库笔记增多导致界面明显卡顿。
    第一版仓库可视化页面优先做笔记级引用图谱，不急于做复杂力导向大图。
    没有引用关系的笔记也必须显示为独立点。
    视图应支持筛选、缩放和局部聚焦，避免所有节点同时挤在一个不可读画面中。

可展望图谱：

    笔记引用图谱：展示笔记之间的引用关系。
    概念图谱：展示全局概念之间的关系。
    块关系图谱：展示定义、组分、自我理解等块之间的结构关系。
    时间演化图谱：展示笔记和引用关系随时间的变化。
    时间演化图谱需要块级写入时间作为基础数据，但该数据模型后续单独设计。

字体和视觉：

    编辑器正文应服务知识输入和阅读，不呈现为普通代码编辑器。
    字体和信息密度应按界面区域分层。


7. 数据需求

数据所有权：

    用户应能在本地完整保存仓库。
    仓库应能恢复笔记、目录树和仓库语法配置。
    普通笔记正文、目录结构和语法配置应保持边界清晰。

原文保留：

    每篇笔记必须保留原始文本。
    每个块必须能追溯到原文位置。
    语法变化不应破坏原文。

索引扩展：

    搜索、块关系和链接查询可以使用派生索引缓存。
    仓库可视化页面和引用图谱必须优先使用派生索引缓存。
    索引缓存不替代原文和仓库配置。


8. 搜索、导入导出与扩展

搜索：

    支持标题和正文搜索。
    扩展目标包括按块类型、定义、组分和自我理解搜索。

链接：

    支持局部概念引用和全局概念引用。
    扩展目标包括反向链接。

导出：

    必须支持纯文本和 JSON。
    扩展目标包括 Markdown、HTML 和 PDF。

导入：

    扩展目标包括 Obsidian / Markdown 导入。

插件：

    扩展目标包括插件系统。
    插件不得破坏原文权威性。


9. 风险

语法过度自由：

    固定底层结构，只允许配置符号到语义类型的映射。

编辑器实现复杂：

    采用原文编辑体验，不追求富文本编辑器。

语法演化导致旧笔记失效：

    笔记绑定明确语法版本。
    解析失败应给出诊断，原文始终保留。

目标语法不兼容导致迁移失败：

    移动前检查符号兼容性。
    目标语法不支持时提示并取消。

数据锁定：

    必须支持 JSON 和纯文本导出。
    数据模型公开。


10. 成功标准

产品成功标准：

    用户可以不用 Markdown 记录复杂概念笔记。
    用户可以通过缩进表达作用域和层级。
    用户可以维护仓库级语法，并让不同笔记使用不同语法。
    用户可以通过结构树判断笔记结构。
    用户可以在笔记之间可靠移动整棵块子树。
    旧数据不会因为语法配置变化而丢失原文。


11. 示例笔记

有限状态机 <状态> \ <输入> \ <输出> \ <状态转移>
    : 用有限数量的状态描述系统行为的模型
    - 状态
        : 系统在某一时刻所处的抽象情况
    - 输入
        : 触发状态变化的外部事件
    - 输出
        : 系统对当前状态或输入的响应
    - 状态转移
        : 从一个状态进入另一个状态的规则
    - Moore machine
        : 输出只由状态决定
    - Mealy machine
        : 输出由状态和输入共同决定
    > 它适合描述受规则控制且状态数量可枚举的过程
    > 用于数字电路设计时，重点不是画图，而是明确状态、输入、输出和转移关系
    ```
    state + input -> next_state + output
    ```
