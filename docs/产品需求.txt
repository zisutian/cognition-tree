产品需求


文档职责：

    记录产品定位、设计原则、核心概念、语法需求、功能范围、风险和成功标准。
    不记录源码目录、开发命令、个人环境、提交计划和工程执行顺序。


1. 产品定位

认知树不是 Markdown 编辑器，也不是传统富文本笔记软件。

认知树的目标是构建一个“可配置语法的认知树编辑器”，用于记录概念、概念群组、定义、组分、自我理解、代码片段和关系。

用户写作时面对的应是思维结构，而不是 Markdown、HTML 或其他排版格式。

Markdown、HTML、PDF、纯文本只作为导出格式，不作为主要写作格式。


2. 设计原则

思维优先：

    编辑器优先服务思维链路，而不是服务文档排版。

缩进即作用域：

    缩进代表父子关系、展开关系或局部语义范围。

符号即语义：

    行首符号、行内符号和块头符号应映射为明确语义。

语法可配置，底层结构稳定：

    可配置符号、语义 type ID、行内规则和受控显示 tone。
    不允许随意配置行、缩进、父子块、解析 role 集合、tone 集合、引用、转义和语法版本语义。

语法文件独立：

    仓库通过独立 syntax/*.toml 持有语法资源。
    笔记通过 syntaxProfileId 和 syntaxVersion 指向语法 profile。
    .ctn 笔记正文不嵌入可执行语法配置。

仓库即知识域：

    仓库是长期知识域和本地文件夹边界，不是单篇笔记的位置。

目录只负责组织：

    文件夹用于浏览、归类、移动和决定新建笔记落点。
    文件夹不绑定语法、不继承语法、不保存解析配置。

本地优先：

    笔记优先保存在本地，用户拥有完整数据。

可导出：

    软件不能制造数据囚笼，笔记必须可以导出为开放格式。


3. 核心概念

仓库：

    长期存在的知识域，接近 Obsidian vault。
    仓库持有笔记原文、目录树、语法资源、笔记元信息和后续索引缓存。

文件夹：

    仓库内的组织结构，只负责组织和浏览。

笔记：

    一篇 .ctn 原文文件。
    笔记记录实际使用的 syntaxProfileId 和 syntaxVersion。

块：

    CTN 的基本结构单位，由一行及其缩进子树组成。
    块范围由 lineNumber 和 endLineNumber 标识。

概念：

    普通行默认表示概念。

定义：

    对概念含义的说明。

组分：

    概念的组成部分、分类项、例子或枚举项。

自我理解：

    用户当前的个人解释，不要求等同于权威定义。

代码块：

    用于记录代码、伪代码、公式或严格文本。

语法配置：

    仓库内的 syntax/*.toml 文件，定义行首 marker、行内规则、role 和 tone。


4. 默认语法

默认块级语法：

    普通行：概念
    :：定义
    >：自我理解
    -：组分、分类、例子和枚举的统一结构项
    ```：代码块 fence

默认行内结构：

    `...`：行内代码
    <...>：当前笔记内的局部概念引用
    [[...]]：全局概念引用
    \：并列分隔

缩进规则：

    Tab 在编辑器中插入四个空格。
    解析器按四个空格作为一个层级。
    缩进表示当前行属于上一层块。


5. 语法配置需求

语法配置以仓库为管理边界，仓库通过 syntax/*.toml 保存多套可用语法。

第一版 TOML 结构：

    id = "ctn-default"
    name = "默认 CTN 语法"
    version = 1
    spaceIndentUnit = 4

    [[markers]]
    marker = "```"
    type = "code"
    label = "代码块"
    role = "code"
    tone = "code"

    [[markers]]
    marker = ":"
    type = "definition"
    label = "定义"
    role = "normal"
    tone = "green"

    [[inlineRules]]
    kind = "paired"
    open = "`"
    close = "`"
    type = "inline-code"
    label = "行内代码"
    tone = "code"

校验规则：

    id 和 name 必须是非空字符串。
    version 和 spaceIndentUnit 必须是正整数。
    markers 必须是非空数组。
    marker、type、label 必须是非空字符串。
    marker rule 必须显式提供 role 和 tone。
    marker 不允许重复。
    type 必须是 ASCII kebab-case 机器语义 ID。
    role 只能是 normal 或 code。
    只有 role = "code" 的 marker 触发 fenced code block。
    tone 只能使用 default、green、blue、amber、red、violet、code。
    inlineRules 必须显式提供，空数组表示禁用所有行内结构。
    inlineRules 支持 paired 和 single。
    schema 之外的字段应被拒绝。

第一版不支持：

    语法继承
    笔记级语法导入
    在 .ctn 正文中定义语法
    自动修改目标笔记语法
    任意 CSS 或任意颜色值

语法文件管理：

    语法文件是仓库资源，不属于笔记目录树。
    语法文件可以新增、编辑和删除。
    保存前必须校验 TOML schema。
    被仓库默认语法或任意笔记引用的语法文件应拒绝删除。
    找不到笔记引用的 profile 时显示明确错误，不使用内置默认语法静默解析。


6. 编辑器需求

基本编辑：

    创建笔记
    编辑 .ctn 原文
    Tab / Shift+Tab 调整层级
    自动识别块类型
    展示诊断
    展示结构树
    支持折叠和滚动

跨笔记块移动：

    第一版只支持同一仓库内跨笔记移动。
    移动单位是整棵块子树，不移动单行碎片。
    第一版只做移动，不做复制。
    移动前检查目标笔记语法是否支持源块子树使用的 marker。
    目标语法不兼容时提示用户，不修改任一笔记。
    拖拽式迁移后续应复用同一套块移动 workflow。

结构视图：

    原文编辑区和结构树应保持联动。
    结构树只展示解析结果，不展示语法配置细节。

字体和视觉：

    编辑器正文应服务知识输入和阅读，不呈现为普通代码编辑器。
    字体和信息密度应按界面区域分层。


7. 数据需求

权威源文件：

    workspace.json 保存仓库元信息、目录树、当前笔记、仓库默认语法引用和笔记元信息。
    notes/*.ctn 保存每篇笔记原文。
    syntax/*.toml 保存仓库可用语法资源。

稳定模型：

    Workspace
    NoteRecord
    NoteTreeNode
    CtnDocument
    CtnBlock
    CtnSyntaxProfile
    CtnMarkerRule
    CtnInlineRule

原文保留：

    每篇笔记必须保留原始 .ctn 文本。
    每个块必须能追溯到原文范围。
    语法变化不应破坏原文。

后续索引：

    SQLite / FTS5 可作为搜索、块关系和链接查询的派生索引缓存。
    索引缓存不替代 workspace.json、notes/*.ctn 和 syntax/*.toml。


8. 搜索、导入导出与扩展

搜索：

    支持标题和正文搜索。
    后续支持按块类型、定义、组分、自我理解搜索。

链接：

    支持局部概念引用和全局概念引用。
    后续支持反向链接。

导出：

    必须支持纯文本和 JSON。
    后续支持 Markdown、HTML 和 PDF。

导入：

    后续支持 Obsidian / Markdown 导入。

插件：

    后续考虑插件系统。
    插件不得破坏原文权威性。

10. 风险

语法过度自由：

    固定底层结构，只允许配置符号到语义类型的映射。

编辑器实现复杂：

    第一版基于 CodeMirror 6 和原文编辑，不从零实现 contenteditable。

语法演化导致旧笔记失效：

    笔记绑定 syntaxProfileId 和 syntaxVersion。
    解析失败应给出诊断，原文始终保留。

目标语法不兼容导致迁移失败：

    移动前检查 marker。
    目标语法不支持时提示并取消。

数据锁定：

    必须支持 JSON 和纯文本导出。
    数据模型公开。


11. 成功标准

第一版成功标准：

    用户可以不用 Markdown 记录复杂概念笔记。
    用户可以通过缩进表达作用域和层级。
    用户可以配置至少 5 种块符号。
    用户可以搜索标题和正文。
    用户可以导出纯文本和 JSON。
    旧数据不会因为语法配置变化而丢失原文。


12. 示例笔记

有限状态机 <状态> \ <输入> \ <输出> \ <状态转移>
    : 用有限数量的状态描述系统行为的模型
    - 状态
        : 系统在某一时刻所处的抽象情况
    - 输入
        : 触发状态变化的外部事件
    - 输出
        : 系统对当前状态或输入的响应
    - 状态转移
        : 从一个状态进入另一个状态的规则
    - Moore machine
        : 输出只由状态决定
    - Mealy machine
        : 输出由状态和输入共同决定
    > 它适合描述受规则控制且状态数量可枚举的过程
    > 用于数字电路设计时，重点不是画图，而是明确状态、输入、输出和转移关系
    ```
    state + input -> next_state + output
    ```
