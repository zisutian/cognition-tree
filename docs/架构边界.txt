架构边界


1. 模块职责

app：

    应用组合根，装配 application、ui、storage 和 editor。activities 只把 application activity 状态适配为 UI slots；workbench 单独组合全局 Frame、问题面板、反馈和 activity 生命周期。

application：

    应用层。workspace 管理普通仓库 session、共享选择、统一导航、语法运行时和 UI 投影；journal 与 todo 分别消费对应系统 session 并持有独立选择和领域命令；journal workspace-reference resolver 按需读取非活动普通仓库的 local-first snapshot，并通过 AppRoot 一次性 `{ repositoryId, noteId, lineNumber: 1 }` destination 完成跨 session 导航；repository 管理普通 catalog、两个系统仓库 session 及仓库问题；workbench 组合可空普通 workspace、两个系统 application 与始终独立存在的 repository application。WorkspaceAnalysis 是唯一普通仓库全仓解析入口，一轮分批扫描同时发布 parsed notes、标题索引、诊断和引用图谱。

ui：

    workbench 界面层，提供活动栏、槽位 Frame、布局控制、全局问题面板、activity 页面、共享组件和样式系统。布局持久化和 resize 交互不进入 application view model。

workspace：

    workspace 业务核心，承载数据模型、命令、查询、索引和语法上下文。

journal：

    位于仓库顶层的前后端共享纯领域核心，承载 Journal v2 内容与 transition 约束、不可变当日序号标题、daily counters、可配置 syntax source、正文命令、月份与选择查询、独立解析索引和仓内引用。日记把顶格无符号行映射为中性的 `body` 语义，不解释普通仓库 catalog 或跨仓导航；qualified reference 的外部解析由 application 完成。journal 只依赖 ctn，不依赖 src、server、contracts、React 或平台运行时。

todo：

    位于仓库顶层的前后端共享纯领域核心，承载 Todo v2 内容与 transition 约束、可配置 syntax source、有序 CTN collection、completion sidecar、结构查询和领域命令。Todo 通过 ctn 解析任务块及缩进层级，保护 `todo-item` 规则的语义 ID/role，并清理已删除 block 的孤立 completion；不依赖 src、server、contracts、React、workspace、journal 或平台运行时。

ctn：

    位于仓库顶层的前后端共享纯领域核心，承载唯一的 canonical/editable 原文解析、结构诊断、metadata reconcile、引用解析、块文本编辑和 syntax profile。顶格无符号规则是可空且带明确 semantic role 的 scoped policy：普通笔记映射为 `concept`，日记映射为 `body`，Todo 禁止无标记正文。ctn 不依赖 src、server、contracts 或平台运行时；application、workspace、journal、todo、editor 和 Local adapter 均消费同一实现。

portable-name：

    位于仓库顶层的纯领域值模块，负责普通笔记标题、文件夹名、仓库名和 Todo 集合名的存储规范化、合法性与唯一键。模块只实现 `trim → NFC → 连续 ASCII 空格折叠`、Unicode 字母/组合标记/数字/空格/`-`/`_` 白名单，以及 `NFKC → en-US lowercase` 引用键；不依赖 workspace、storage、server、React 或平台文件系统。

storage：

    前端持久化边界。repository 的通用 versioned repository 将 raw remote backend 与 application 使用的 local-first repository 分开，定义 local draft CAS、远端同步结果、缓存数据和离线恢复策略；普通 Workspace 与系统仓库以各自 codec、validator 和 DTO 适配该机制。browser 与 HTTP adapter 实现外部读写；runtime 是唯一组合 adapter 的位置。普通 catalog 发布可创建 adapter，负责列出、创建、重命名、删除和按 id 打开仓库；系统 catalog 固定发布日记与代办，只允许 list、open 和 retry。两类 catalog 均以 adapter 对应的结构化 location 表达存储位置。

editor：

    编辑器技术适配，承载 CodeMirror 组件、扩展、装饰、诊断提示、引用点击识别和多行块键位行为。

server：

    仓库执行端。repository 定义普通 store/catalog 端口、v4 内容、syntax catalog 语义校验、revision 与删除结果，并定义两个固定 purpose 的系统仓库文件 store、CAS 和受保护 catalog；catalog 组合健康普通仓库和带 adapter、lifecycle 状态的单仓问题，统一分配 repository ID 与名称冲突投影；api 负责 HTTP、统一错误与请求安全；local adapter 管理可见 working tree、隐藏 `.ctn/` 内部事实、稳定扫描、身份协调、WAL、独占 writer 和原子删除；WebDAV adapter 管理安全连接 registry、目标网络边界、不可变 generation、lease、ETag CAS 与 deletion tombstone；index 是唯一组合根。

contracts：

    前后端中立的 wire contract，分别负责普通仓库与系统仓库的 catalog、请求、快照、结构化 location 和提交结果运行时解析。系统仓库 contract 固定 purpose、受保护 descriptor 及 Journal/Todo v2 的精确 wire shape，不包含删除、重命名或创建请求。普通 descriptor 以 `labelIssue: conflict | reserved | nonportable | null` 投影名称问题。


2. 依赖方向

    app -> application、ui、storage、editor
    ui -> application、editor
    application -> workspace、ctn、storage、portable-name
    application -> journal
    application -> todo
    workspace -> ctn、portable-name
    journal -> ctn
    todo -> ctn、portable-name
    storage -> workspace、contracts、portable-name
    storage -> journal
    storage -> todo
    editor -> ctn
    server -> contracts、portable-name、Node HTTP、文件系统
    server/repository/workspaceRepositoryContentValidation -> ctn
    server/repository/systemRepositoryStore -> journal
    server/repository/systemRepositoryStore -> todo
    server/adapters/local -> ctn

    storage/repository 不依赖 storage/adapters 或 storage/runtime。
    storage/adapters/browser 与 storage/adapters/http 互不依赖。
    server/repository 不依赖 server/api、server/catalog 或 server/adapters。
    server/adapters/local 与 server/adapters/webdav 互不依赖。


3. 数据流

    server 将 repository id 解析为 catalog 中的仓库 adapter，读取显式 content 与 sha256 revision；repository validator 对 syntax catalog 中每份 TOML 和规范化名称唯一性作统一语义校验；Local 从真实目录、可见 `.ctn` 正文、隐藏 sidecar 与 `.ctn/syntax/` 重建 canonical content，以 `.ctn/repository.json` head 的 durable atomic replace 发布 WAL target；WebDAV generation 保存同构 syntax catalog，并以 current pointer 的 ETag CAS 发布。WebDAV registry 在本地安全状态中保存动态连接，启动时只加载连接描述，实际网络访问由对应 store 延迟执行。
    contracts 在 storage 和 server 边界分别解析同一普通仓库或系统仓库 wire shape。
    system-journal 与 system-todo 在 wire 解析之后分别经过 v2 领域语义 validator。系统存储按 purpose 保存 epoch；发现缺失或旧 v1 epoch 时，只清除该 purpose 的旧 content 与 local-first draft/cache 并 provision 空 v2，Browser 在单个 IndexedDB transaction 内完成，HTTP 幂等替换后最后发布 epoch。该过程不读取、迁移、备份或报告旧格式；已经进入 v2 后的损坏内容和未知未来 epoch 则保留原值并形成故障。首次 load 校验单份 v2 content；已有本地事实的前向 refresh、local stage、Browser remote CAS 和 HTTP file commit 同时校验前后 revision transition。Journal 的 entry/block identity、不可变 sequence、daily counter 单调性和 canonical metadata 保持稳定；Todo 的 collection/block identity、CTN source、syntax 保护和 completion transition 保持一致。校验失败时保留原内容。
    storage 在 IndexedDB transaction 中先以 draft revision CAS stage 最新本地 content，再由 backend 对远端 sha256 revision 提交。offline、conflict 与 sync-error 是显式同步结果，远端 409 不进入 application。
    HTTP Local 在首次加载和手动 reload 时优先扫描服务端 working tree；没有 pending draft 时安装磁盘 revision，存在 pending 且磁盘 revision 变化时保留 draft 并形成 ready session 内的 conflict。同步提交也先扫描磁盘并校验 base revision。
    application/repository 的通用保存队列维护每个 ready session 的独立持久化状态与保存 worker。普通 workspace command 和系统仓库领域 mutation 同步更新各自内存，随后立即 stage 本地 draft，500ms debounce 后同步远端；普通仓库切换只等待其本地持久化，不停止或重建系统 session。
    application 在删除当前仓库前冻结 workspace command、排空 local stage 并等待已开始的同步；删除失败时恢复原 ready session 与保存队列。catalog mutation 成功后清理对应 descriptor、issue 和本地 cache。
    Local adapter 只在首次加载、同步提交和显式重新扫描时识别外部修改，不建立 watcher 或 SSE。扫描以路径、唯一 inode、唯一旧 source hash 或子树 signature 协调身份；外部正文变化形成确定性 text edits，再交给 CTN canonical metadata reconcile。无法证明同一对象时按删除加新建处理。
    Local 与 Browser 删除以原子提交点移除托管内容。Local 删除和目录操作保护非 `.ctn` unmanaged 文件与 symlink；WebDAV 的 remove-connection 只移除本地 registry 与 cache；delete-managed-data 以 current ETag CAS 发布永久 tombstone，随后异步清理托管 generation，catalog 以 deleting issue 表达未完成清理。
    application 将普通仓库 canonical CTN 投影为 editable source，通过唯一 WorkspaceAnalysis 分批解析一次，并把诊断、结构定位、标题候选和引用图谱映射到 activity view model。Journal application 直接消费独立 system-journal session，以自身 parse index、选择、正文行号投影、仓内引用和 diagnostics 形成日记 view model；qualified reference 解析器只按需打开命名普通仓库的 local-first snapshot，从 canonical note header 建标题索引，不创建非活动 workspace session，也不全量扫描 WebDAV。离线但有缓存时继续使用缓存，loading 期间不提前报告 unresolved；仓库不存在、名称异常、仓库不可读、笔记不存在和同名笔记分别形成 Journal diagnostics。跨仓边不进入普通仓库引用图谱，仓库或笔记重命名也不跨独立 CAS 改写日记 source。目标导航先排空当前普通 session，再切换仓库，等待新 session 挂载后进入 Notes 并选择目标笔记。Todo application 直接消费独立 system-todo session，以 CTN parse index、collection 选择、结构 mutation 和 completion sidecar 形成代办 view model；二者都不进入 WorkspaceAnalysis。
    app 根同时装配可空普通 workspace、普通 catalog、Journal application、Todo application 和两个固定系统 session；普通仓库缺失或挂载失败时仍渲染完整 Workbench。activity adapter 将局部 view model 交给 ui 生成 activity slots；仓库 activity 使用 UI-only discriminated selection 组合新建、普通仓库、普通仓库故障和系统仓库的 master-detail，设置 activity 只承载工作台界面偏好。全局问题面板由 app/workbench 组合，不进入 activity slots，也不经 activity adapter 传递。普通活动投影 workspace diagnostics；Repository 合并 workspace diagnostics、普通/系统仓库问题和名称问题；Journal 投影自身文档、语法、仓内及跨仓引用诊断；Todo 投影自身语法和 CTN 诊断；Syntax 根据当前编辑 owner 投影 profile diagnostics，并仅在编辑活动普通语法时附加 workspace diagnostics；Settings 不挂载问题面板。仓库问题点击只定位左侧 selection 并在右侧展示详情，破坏性操作不进入问题行。
    editor 接收可编辑文本、scoped semantic role 和语法展示数据，为当前编辑状态生成 CodeMirror 装饰、诊断提示、引用交互和 Todo checkbox。概念强调只由 `concept` role 触发；日记 `body` 不使用概念装饰；Todo checkbox 与详情结构树都读写 completion sidecar。日记 body mode 只把正文放入 CodeMirror，并以不可编辑的 synthetic title 解析后将所有行号投影回正文。editor 不负责保存或解释块元数据。
    workspace 和 ctn 负责结构、语义和派生数据的确定性计算。
