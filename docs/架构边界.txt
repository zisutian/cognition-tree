架构边界


1. 模块职责

app：

    应用组合根，装配 application、ui、storage 和 editor。

application：

    workspace 应用层，管理 session、共享选择与语法运行时，并按 activity 管理页面状态和 UI 投影。

ui：

    workbench 界面层，组合活动栏、槽位布局、activity 页面、共享组件和样式系统。

workspace：

    workspace 业务核心，承载数据模型、命令、查询、索引和语法上下文。

ctn：

    CTN 核心能力，承载原文解析、结构诊断、引用解析、块文本编辑和 syntax profile。

storage：

    前端持久化边界。repository 定义端口、缓存数据和离线恢复策略；browser 与 HTTP adapter 实现外部读写；runtime 是唯一组合 adapter 的位置。catalog 负责列出、创建和按 id 打开仓库；repository 以带仓库位置和 revision 的快照读取 workspace 数据与仓库语法 source，并提交完整内容新版本。

editor：

    编辑器技术适配，承载 CodeMirror 组件、扩展、装饰、诊断提示、引用点击识别和多行块键位行为。

server：

    仓库执行端。repository 定义 store/catalog 端口及共享 manifest、路径、revision 规则；catalog 组合可用仓库；api 负责 HTTP 与请求安全；local 和 WebDAV adapter 负责具体 I/O；index 是唯一组合根。

contracts：

    前后端中立的 wire contract，负责 repository 请求、快照和提交结果的运行时解析。


2. 依赖方向

    app -> application、ui、storage、editor
    ui -> application、editor
    application -> workspace、ctn、storage
    workspace -> ctn
    storage -> workspace、contracts
    editor -> ctn
    server -> contracts、Node HTTP、文件系统

    storage/repository 不依赖 storage/adapters 或 storage/runtime。
    storage/adapters/browser 与 storage/adapters/http 互不依赖。
    server/repository 不依赖 server/api、server/catalog 或 server/adapters。
    server/adapters/local 与 server/adapters/webdav 互不依赖。


3. 数据流

    server 将 repository id 解析为配置 catalog 中的仓库 adapter，再生成包含仓库位置、workspace、syntax source 和 revision 的完整快照，并以事务提交完整新版本。
    contracts 在 storage 和 server 边界解析同一 repository wire shape。
    storage 将仓库快照和提交结果接入前端 repository 端口，过期 revision 不覆盖当前仓库；离线缓存、恢复提交和远端冲突判定都停留在 repository adapter 内。
    application 维护 session、单一保存队列、共享 runtime 和 activity controller，消费 repository 提供的 online、offline 或 conflict 状态，并按当前 activity 生成局部 view model。
    application 将持久化 CTN 投影为不含保留元数据行的可编辑文本，并把诊断、结构定位和引用跳转映射到编辑行；editor 不负责保存或解释块元数据。
    ui 根据局部 view model 生成 activity slots，并通过回调触发 application 命令。
    editor 接收 ui 和 application 给出的文本、诊断和语法展示数据。
    workspace 和 ctn 负责结构、语义和派生数据的确定性计算。
