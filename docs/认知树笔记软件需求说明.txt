认知树笔记软件需求说明

版本：0.1
日期：2026-05-20
状态：草案


1. 产品定位

本软件不是 Markdown 编辑器，也不是传统富文本笔记软件。

本软件的目标是构建一个“可配置语法的认知树编辑器”，用于记录用户认知内的概念、概念群组、条件、定义、疑问、自我理解、证据、例子、关系等内容。

用户写作时面对的应是思维结构，而不是 Markdown、HTML 或其他排版格式。

Markdown、HTML、PDF、纯文本只作为导出格式，不作为主要写作格式。


2. 核心问题

用户在 Markdown 中记录复杂认知时，需要不断进行格式映射：

    当前内容是标题、列表、引用、代码块、表格，还是 frontmatter？
    条件作用域应该如何表示？
    缩进层级是否会被 Markdown 误解？
    某个符号到底是排版符号，还是认知语义？

这些映射会打断思维链路。

本软件需要减少这种额外负担，使用户可以直接按自己的认知结构输入内容。


3. 设计原则

3.1 思维优先

编辑器应优先服务于思维链路，而不是服务于文档排版。

3.2 缩进即作用域

缩进代表父子关系、展开关系、条件作用范围或局部语义范围。

3.3 符号即语义

行首符号、行内符号、块头符号应映射为明确的语义类型，例如定义、疑问、组分、自我理解、注释、条件。

3.4 语法可配置，底层结构稳定

用户可以配置符号规则，但软件内部的数据结构应保持稳定。

可配置：

    符号长什么样
    符号对应什么语义
    某类块能否有子块
    某类块如何显示
    某类块如何导出

不可随意配置：

    行
    缩进
    父子块
    块类型
    行内标记
    引用
    转义
    语法版本

3.5 本地优先

笔记应优先保存在本地，用户拥有完整数据。

3.6 可导出

软件不能制造数据囚笼。所有笔记必须可以导出为开放格式。


4. 核心概念

4.1 笔记

笔记是一个独立认知主题的容器。

一条笔记包含标题、元信息、语法配置版本、若干块。

4.2 块

块是编辑器的基本单位。

每个块包含：

    唯一 ID
    块类型
    原始文本
    解析后的正文
    行内标记
    子块
    属性
    创建时间
    修改时间

4.3 概念

概念通常是一个词语或名词短语，用于描述物体、抽象对象、存在形式、状态、性质或方法。

4.4 概念群组

概念群组是一组概念的交互，通常含有动词或关系。

示例：

    状态转移影响输出
    模型生成位置 token
    条件限制定义适用范围

4.5 条件

条件不是普通说明，而是作用域。

条件块下的所有子块默认只在该条件下成立。

4.6 定义

定义用于说明一个概念是什么。

4.7 组分

组分用于描述一个概念包含哪些组成部分、分类、例子或枚举项。

4.8 疑问

疑问用于记录当前不确定、待验证、待实验、待查证的内容。

4.9 自我理解

自我理解用于记录用户当前的个人解释，不要求等同于权威定义。

4.10 注释

注释用于补充说明某一行、某一块或某一局部语义。


5. 默认语法草案

5.1 块头

    概念名(别名、英文、缩写)[组分 A \ 组分 B]

含义：

    概念名是当前块的主体。
    圆括号内表示别名、英文、缩写或小解释。
    方括号内表示小体量组分、举例或枚举。
    反斜杠表示并列概念。

5.2 行首符号

    :        定义
    [?]      疑问
    [组分]   组分论述
    [分类]   分类论述
    [例子]   举例
    [条件]   条件说明
    [证据]   证据
    [反例]   反例
    [注]     注释
    [理解]   自我理解

5.3 行内符号

    (...)    别名、英文、缩写、小解释
    [...]    小体量组分或举例
    <...>    局部概念引用
    [[...]]  全局概念引用
    \        并列
    *        可选
    !        否定或不支持
    @        所见即所得，不参与自动改写

5.4 缩进

缩进表示当前行属于上一层块。

默认使用 Tab 作为一个缩进单位。

渲染时可以显示为树状层级。


6. 语法配置需求

6.1 语法配置文件

软件应支持多个语法配置方案。

每个语法配置方案包含：

    配置 ID
    配置名称
    版本号
    缩进规则
    块规则
    行内规则
    转义规则
    显示规则
    导出规则

6.2 示例配置结构

    syntaxProfileId: my-cognition-syntax
    version: 1
    indent:
        unit: tab
        meaning: parent-child-scope
    blockRules:
        marker: :
        position: line-start
        type: definition
        displayName: 定义
    inlineRules:
        open: (
        close: )
        type: alias-or-condition

6.3 旧笔记兼容

每条笔记必须记录：

    syntaxProfileId
    syntaxVersion

当用户修改语法配置后，旧笔记应能选择：

    继续使用旧语法打开
    迁移到新语法
    仅改变显示，不改原始文本

6.4 规则冲突检测

当用户配置符号时，软件应检测冲突。

示例：

    同一位置不能同时将 : 定义为 definition 和 condition。
    行内符号不能出现无法闭合的成对规则。
    长符号应优先于短符号解析，例如 <->> 应优先于 <>。


7. 编辑器需求

7.1 基本编辑

必须支持：

    输入文字
    Enter 创建同级块
    Tab 增加缩进
    Shift+Tab 减少缩进
    Backspace 合并块
    复制粘贴块
    拖拽调整块层级
    折叠和展开子块

7.2 块类型识别

用户输入行首符号后，编辑器应自动识别块类型。

示例：

    输入 : 后，该块识别为 definition。
    输入 [?] 后，该块识别为 question。
    输入 [理解] 后，该块识别为 personal-understanding。

7.3 块类型手动修改

用户应能通过快捷键、命令面板或右键菜单修改块类型。

7.4 条件作用域显示

条件块应在视觉上明确提示其作用范围。

例如：

    左侧竖线
    背景色
    折叠范围
    作用域边界提示

7.5 原文与结构双视图

编辑器应至少支持两种视图：

    原文视图：接近用户输入的缩进符号格式。
    结构视图：显示解析后的块类型、层级、关系。

7.6 可选的无符号输入

用户也应能通过菜单选择块类型，而不是必须输入符号。


8. 数据存储需求

8.1 存储方式

建议第一版优先使用本地文件库。

    workspace.json 保存仓库树、当前笔记、语法配置引用和笔记元信息。
    notes/*.ctn 保存每篇笔记的原文内容。
    SQLite / FTS5 后续作为搜索、块关系和链接查询的索引缓存。

8.2 后续索引缓存表

notes:

    id
    title
    type
    syntaxProfileId
    syntaxVersion
    createdAt
    updatedAt
    archivedAt

blocks:

    id
    noteId
    parentId
    orderIndex
    type
    rawText
    parsedText
    props
    createdAt
    updatedAt

links:

    id
    sourceBlockId
    targetNoteId
    targetBlockId
    linkText
    linkType

syntax_profiles:

    id
    name
    version
    configJson
    createdAt
    updatedAt

8.3 原始文本保留

每个块应保留 rawText。

即使解析器升级，也不能丢失用户原始输入。


9. 搜索与导航需求

9.1 全文搜索

支持按标题、正文、原始文本搜索。

9.2 类型搜索

支持按块类型搜索。

示例：

    查找所有疑问
    查找所有定义
    查找所有自我理解
    查找所有条件块

9.3 链接跳转

支持全局概念引用。

示例：

    [[有限状态机]]
    [[状态转移]]

9.4 反向链接

支持查看哪些笔记或块引用了当前概念。

9.5 层级导航

支持按块树查看当前笔记结构。


10. 导入导出需求

10.1 必须支持的导出格式

    JSON
    纯文本
    Markdown
    HTML

10.2 后期支持

    PDF
    DOCX
    OPML

10.3 Markdown 导出原则

Markdown 只是导出格式。

导出时可以将：

    定义块导出为普通段落或引用
    疑问块导出为任务列表或特殊小节
    条件块导出为缩进列表或标题层级
    双链导出为 Markdown 链接或纯文本

10.4 Obsidian 导入

后期应支持从 Obsidian 文件夹导入 Markdown。

导入时尽量识别：

    文件名为概念名
    [[双链]]
    ![[附件]]
    [组分] 这类旧格式小节
    #待完善、??? 等不确定标记


11. 插件与扩展需求

11.1 插件目标

允许用户扩展：

    块类型
    显示方式
    导出器
    导入器
    搜索过滤器
    命令

11.2 插件语言

建议使用 JavaScript 或 TypeScript 插件。

11.3 插件边界

插件不能破坏原始数据。

插件对数据库的写操作应经过权限声明。


12. 技术路线建议

12.1 桌面端

第一阶段采用：

    Tauri 2
    Vite
    React
    TypeScript
    Rust
    本地文件库
    CodeMirror 6

备选：

    Electron
    TypeScript
    SQLite
    ProseMirror
    TipTap
    Lexical

说明：

    第一阶段优先实现本地桌面端。
    Tauri 2 负责桌面壳和系统能力。
    React 负责应用界面。
    CodeMirror 6 负责 .ctn 原文编辑、缩进、快捷键、语法装饰和作用域提示。
    Rust 负责 Tauri commands、本地文件读写和系统能力。
    本地文件库负责笔记原文、仓库树和语法配置元信息。
    SQLite / FTS5 搜索索引作为后续增强，不作为第一阶段必须依赖。

12.2 编辑器核心

不建议从零实现 contenteditable。

第一阶段基于 CodeMirror 6 构建语义文本编辑器。

原因：

    本软件的核心输入是 .ctn 原始文本。
    缩进、行首符号、行内符号和语法配置是主要语义来源。
    CodeMirror 6 更适合处理文本、缩进、装饰、折叠、快捷键和结构视图联动。
    ProseMirror、TipTap 或 Lexical 可作为后续结构化块编辑器候选，但不作为第一阶段主依赖。

第一阶段编辑器至少应提供：

    原文视图
    块类型识别
    缩进层级显示
    条件作用域提示
    结构视图或大纲视图
    与解析器输出联动的语法装饰

12.3 解析器

解析器应独立于 UI。

第一阶段解析器使用 TypeScript 实现，直接服务 CodeMirror 6 装饰、结构视图和 Vitest 测试。

后续如果需要 CLI、批量迁移或后台索引一致性，可考虑增加 Rust 版本解析器，或将解析器核心迁移到 Rust。

解析流程：

    原始文本
    按行切分
    计算缩进层级
    识别行首符号
    识别行内符号
    构建块树
    输出语义块模型

16. 风险

16.1 语法过度自由

如果允许用户配置完整语法，解析器会不可控。

缓解：

    固定底层语法结构。
    只允许配置符号到语义类型的映射。

16.2 编辑器实现复杂

结构化编辑器比普通文本框复杂。

缓解：

    第一版先实现块树编辑。
    不急于实现所有富文本能力。

16.3 用户规则演化导致旧笔记失效

缓解：

    每条笔记绑定 syntaxProfileId 和 syntaxVersion。
    保留 rawText。
    提供迁移器。

16.4 数据锁定

缓解：

    必须支持 JSON 和纯文本导出。
    数据模型公开。


17. 成功标准

第一版成功标准：

    用户可以不用 Markdown 记录一条复杂概念笔记。
    用户可以通过缩进表达条件和层级。
    用户可以配置至少 5 种块符号。
    用户可以搜索定义、疑问、自我理解。
    用户可以导出纯文本和 JSON。
    旧数据不会因为语法配置变化而丢失。


18. 示例笔记

有限状态机(FSM, Finite State Machine)[状态 \ 输入 \ 输出 \ 状态转移]
    : 用有限数量的状态描述系统行为的模型
    [组分]
        <状态>
            : 系统在某一时刻所处的抽象情况
        <输入>
            : 触发状态变化的外部条件
        <输出>
            : 系统对当前状态或输入的响应
    [分类]
        Moore machine
            : 输出只由状态决定
        Mealy machine
            : 输出由状态和输入共同决定
    [理解]
        它适合描述受规则控制且状态数量可枚举的过程
    [?]
        复杂系统中如何确定状态粒度？
    (用于数字电路设计时)
        [理解]
            重点不是画图，而是明确状态、输入、输出和转移条件


19. 当前结论

该软件应优先实现为本地桌面端认知树编辑器。

核心竞争力不在排版，而在：

    可配置语法
    缩进作用域
    语义块
    稳定数据模型
    可导出
    可迁移

这套系统的目标是让用户直接记录思维链路，而不是先把思维翻译成 Markdown。
